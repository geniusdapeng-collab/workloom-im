# 需求澄清与转运（与 ai-pm V3 深度耦合）

## 一、何时调用
- 意图判定为 feature_request 时；客户对已确认需求提出变更时；流水线关键节点回传时。

## 二、澄清框架（缺什么问什么，多轮对话）
| 维度 | 典型追问 |
|---|---|
| 场景 | "这个能力主要解决什么场景的问题？能举个最近的例子吗？" |
| 使用者 | "谁来用？您的团队里是什么角色？多频繁？" |
| 验收期望 | "做到什么程度您算满意？有没有参照？" |
| 约束 | "有没有时间要求？预算/积分消耗有顾虑吗？" |

## 三、执行步骤
1. **澄清**：按框架补齐四维，产出《需求确认单》（目标/场景/使用者/验收期望/约束/预估排期说明）；
2. **对焦**：确认单发送客户；客户可修改（回到澄清）或显式确认——**客户显式确认是进入研发的唯一闸门**；
3. **绑定**：确认单原文 + 客户确认记录 + 关联工单，三方绑定落库；
4. **注入（R-PL3 人审）**：需求转运官将确认需求注入 ai-pm V3 产品经理负责制研发流水线（V3"需求三类入口"之"平台工单入口"），建立 `ticket ↔ requirement` 双向关联；多家客户同类需求聚合为同一 requirement，需求热度（客户数×健康分×ARR 权重）供 PM 排期；
5. **回传**：流水线关键节点（已立项/开发中/评测中/待发布/已发布）1 分钟内回传工单并推送客户；
6. **交付**：发布完成自动推送交付说明（新增能力/用法/注意事项/生效版本）→ 客户验收 → 关单 → 第 3 天回访；
7. **回流**：回访反馈三路分流——问题→新工单；改进建议→eval 集；可复用问答→知识库候选；行业通用 → 交行业包运营组灰度分发。

## 四、边界与围栏
- 注入研发走 R-PL3 人审（平台 PM 拍板）；PM 驳回需给出理由并回传客户（"暂不做的原因"也是服务）；
- 确认后变更需求：生成变更记录，重走确认，禁止直接改单注入。

## 五、与其他技能的协作
- 上游：intent-triage；下游：ai-pm V3 流水线（requirement-analyst 接单）、rollout-watch（行业通用灰度）、kb-harvest（回访沉淀）。
